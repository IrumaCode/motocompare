# Fase 7: Integración continua con GitHub Actions

## Qué se construyó

- **Un workflow** (`.github/workflows/ci.yml`) que GitHub ejecuta solo en cada pull request y en cada push a `main`.
- **Dos jobs en paralelo**, cada uno en una máquina Ubuntu nueva:

  | Job                       | Pasos                                                           | Necesita              |
  | ------------------------- | --------------------------------------------------------------- | --------------------- |
  | **Lint, types and tests** | `pnpm lint`, `pnpm typecheck`, `pnpm format:check`, `pnpm test` | nada                  |
  | **Database tests**        | `pnpm test:db`                                                  | PostgreSQL (servicio) |

- **Un experimento de CI en rojo**: un PR desechable rompió a propósito el redondeo a pesos (`Math.round` → `Math.floor`). El job de pruebas falló y el de base de datos pasó. Luego se revirtió el cambio, el check volvió a verde y el PR se cerró sin fusionar.

## Cómo encaja todo

```
git push ──► GitHub detecta .github/workflows/ci.yml
               │  evento: pull_request  (o push a main)
               ├─ job "checks"    (ubuntu-latest)
               │    checkout ─► pnpm ─► Node 24 + caché ─► install ─► lint ─► typecheck ─► format ─► test
               └─ job "db-tests"  (ubuntu-latest)
                    services: postgres:18-alpine (espera a pg_isready)
                    checkout ─► pnpm ─► Node 24 + caché ─► install ─► test:db
                                                   │
               resultado ──► check verde ✅ / rojo ❌ en el PR
```

## Decisiones clave y por qué

| Decisión                                     | Por qué                                                                                                                                                                                     |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`pull_request` + `push` a `main`**         | El PR avisa antes de fusionar; el push a `main` confirma que lo fusionado sigue en verde. No se escucha cada push a cualquier rama para no gastar minutos dos veces por el mismo commit.    |
| **`concurrency` con `cancel-in-progress`**   | Si haces dos push seguidos a un PR, el primer run se cancela: solo importa el último commit y se ahorran minutos. En `main` no se cancela, para que cada commit fusionado quede verificado. |
| **`timeout-minutes: 10` por job**            | Por defecto un job puede durar 6 horas. Si algo se cuelga (por ejemplo la base de datos), el límite corta el run antes de gastar la cuota gratuita.                                         |
| **`permissions: contents: read`**            | Principio de mínimo privilegio: el workflow solo lee el código. Si una acción de terceros fuera maliciosa, no podría escribir en el repo.                                                   |
| **`pnpm install --frozen-lockfile`**         | Falla si `pnpm-lock.yaml` no coincide con los `package.json`. El CI instala exactamente lo mismo que tu máquina, sin actualizar versiones a escondidas.                                     |
| **`pnpm/action-setup` lee `packageManager`** | La versión de pnpm sale de `package.json`, así que hay una sola fuente de verdad para local y CI.                                                                                           |
| **`cache: pnpm` en `setup-node`**            | Guarda la carpeta de paquetes de pnpm entre runs. El `install` pasa de descargar todo a copiar lo que ya tiene.                                                                             |
| **PostgreSQL como `service` del job**        | Es el equivalente a `docker compose` en el CI: una base desechable que vive solo durante el job. El `health-cmd` evita que las pruebas arranquen antes de que la base acepte conexiones.    |
| **Dos jobs en vez de uno**                   | Corren en paralelo, así que el total tarda lo que el más lento. Además, el check que falla dice dónde mirar: lógica y estilo, o SQL.                                                        |
| **`format:check` en el CI**                  | `pnpm format` modifica archivos; `format:check` solo verifica. En el CI nunca se corrige nada: se avisa y el desarrollador corrige en local.                                                |

## Alternativas descartadas

- **Un solo job con todo**: más simple, pero más lento (todo en serie) y el check no dice qué parte falló.
- **Acción compuesta para los pasos repetidos** (checkout, pnpm, Node, install): con solo dos jobs, la duplicación es de 4 líneas. Extraerla añade un archivo y una indirección sin beneficio real todavía (YAGNI).
- **Matriz de versiones de Node**: tiene sentido en librerías que otros instalan. Esta app corre en una sola versión, así que una matriz solo multiplicaría los minutos.
- **Otros proveedores de CI** (GitLab CI, CircleCI): el código ya vive en GitHub y Actions no necesita otra cuenta. En repos privados el plan gratuito incluye una cuota de minutos al mes (en repos públicos es ilimitado), por eso el workflow ahorra minutos con `concurrency` y caché.

## Lo que encontró el CI (y por qué falló al principio)

- **Run 1, formato**: el propio `ci.yml` no pasaba Prettier. El CI revisa todo el repo, incluido su propio archivo de configuración.
- **Run 2, una prueba inestable ("flaky")**: en tu máquina pasaba, en el runner de GitHub (más lento) no. La prueba usaba `getByRole` para el botón "Kawasaki", que busca **una sola vez**, antes de que llegaran los filtros de marcas. Se cambió por `findByRole`, que **espera** hasta que el elemento aparece. Es un caso típico: el CI destapa condiciones de carrera que tu equipo rápido esconde.
- **Experimento en rojo**: `8199 × 3156.32 = 25 878 667.68`. Con `round` da 25 878 668 y con `floor` da 25 878 667, así que la prueba de `price-service` falló y el PR quedó marcado en rojo antes de llegar a `main`.

## Comandos que vale la pena recordar

```bash
gh pr checks <número> --watch   # ver los checks de un PR en vivo
gh run list --limit 5           # últimos runs del workflow
gh run view <id> --log-failed   # solo el log de los pasos que fallaron
gh run rerun <id> --failed      # repetir solo los jobs que fallaron
git revert HEAD --no-edit       # deshacer el último commit con un commit nuevo (sin reescribir historia)
gh pr close <número> --delete-branch  # cerrar un PR sin fusionar y borrar su rama
git fetch --prune               # olvidar ramas remotas que ya no existen en GitHub
```

## Para estudiar más

1. **Branch protection / rulesets**: hacer que GitHub **impida** fusionar un PR si los checks están en rojo (hoy el CI avisa, pero no bloquea). En el plan gratuito de GitHub solo está disponible para repos públicos.
2. **Pruebas inestables (flaky tests)**: por qué aparecen (tiempos, orden, estado compartido) y cómo detectarlas, por ejemplo repitiendo la suite varias veces.
3. **Seguridad en GitHub Actions**: fijar acciones por SHA en vez de por versión, `permissions` por job y cómo se manejan los _secrets_ (lo necesitaremos en la Fase 8 para desplegar).
